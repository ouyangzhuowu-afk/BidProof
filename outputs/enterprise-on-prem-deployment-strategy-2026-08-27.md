# BidProof 企业本地部署策略

日期：2026-08-27

## 推荐路线

采用“企业内网专用 Linux 虚拟机 + 单实例 BidProof 容器 + 内网 TLS 反向代理 + 加密数据卷 + 异机备份”的部署方式。

这条路线适合当前 FastAPI、SQLite 和本地文件目录架构，能够把应用、运行数据和公网试点环境分离，也不会制造 SQLite 可以多副本运行的假象。首期只运行一个应用实例；需要横向扩容或更高可用时，必须先完成 PostgreSQL、对象存储和外部任务队列迁移。

```text
企业用户
   |
内网 DNS + HTTPS 443
   |
反向代理（企业证书、访问日志、请求大小限制）
   |
BidProof 容器（单实例，可信身份头关闭）
   |
加密持久卷 /srv/bidproof/data
   |-- bid_agent.sqlite3
   |-- uploads/
   |-- job-staging/
   `-- backups/
           |
           `-- 每日复制到另一台 NAS/备份服务器
```

## 运行配置

生产环境至少固定以下变量：

```dotenv
BIDPROOF_DATA_ROOT=/data
BIDPROOF_ALLOW_TRUSTED_HEADERS=0
BIDPROOF_MAX_UPLOAD_BYTES=52428800
```

- 容器内 `/data` 必须映射到企业加密磁盘，不得使用容器临时层。
- 应用端口只暴露给反向代理网络，不直接开放到办公网或互联网。
- 首个企业管理员通过初始化页创建；后续所有访问必须使用会话 Cookie 和角色权限。
- 密钥只从企业密钥管理器或容器 secret 注入，不写入镜像、Compose 文件或项目目录。
- 当前 SQLite 只允许一个应用实例写入，不得把副本数调到 2 以上。

## OCR 数据边界

当前 Qwen OCR adapter 会把需要 OCR 的页面图像发送到配置的外部端点。

- 企业允许受控外联：仅放行批准的 OCR 域名，密钥由企业密钥管理器注入，并在隐私说明中记录数据流向。
- 企业要求完全离线：保持 `BID_OCR_PROVIDER=disabled`，扫描页降级为人工复核；若要保留 OCR 能力，需另行接入企业批准的本地 OCR adapter。

在本地 OCR adapter 完成前，不能把“部署在企业内网”表述为“所有文档处理均不出网”。

## 上线步骤

1. 准备一台专用虚拟机，使用企业支持的长期维护 Linux；初始资源建议从 4 vCPU、16 GB 内存和 200 GB 加密数据盘开始，真实容量须由文件规模和并发压测校准。
2. 从固定版本构建镜像并推送到企业私有镜像仓库；生产部署引用不可变镜像摘要，不使用浮动 `latest`。
3. 挂载 `/srv/bidproof/data:/data`，设置仅服务账号可读写的权限，配置日志轮转和磁盘容量告警。
4. 由 Nginx、Caddy 或企业现有网关终止 TLS；只开放 443，管理端口仅允许运维网段访问。
5. 启动单实例应用，访问 `/healthz?detail=true` 检查数据库、作业和备份状态，完成管理员初始化。
6. 用非生产样本完成上传、扫描、复核人分配、报告导出、归档、恢复和权限隔离验收。
7. 创建并验证首份备份，再做一次隔离恢复演练；恢复结果通过后才接收正式文件。

## 备份与恢复

- 建议目标：每日一次应用级在线备份，拟定 `RPO <= 24 小时`；每月一次隔离恢复演练，拟定 `RTO <= 4 小时`。这是建议目标，不是当前已证明的 SLA。
- 备份必须同时包含 SQLite 数据库和上传文件，并保留现有 SHA-256 清单与 `PRAGMA integrity_check` 结果。
- 本机备份目录不是灾备。验证通过的备份应复制到另一台 NAS、备份服务器或离线介质，并启用不可变保留策略。
- 恢复只能由离线运维流程执行：先停止应用，验证备份，在隔离目录恢复并检查任务数与文件数，再切换数据目录。

## 发布与回滚

每次升级执行固定流程：

1. 锁定镜像摘要和变更说明。
2. 创建并验证升级前备份。
3. 在预生产环境运行全量测试、数据库迁移和浏览器烟测。
4. 业务低峰停止旧容器并启动新版本。
5. 验证登录、任务列表、原文件下载、扫描作业和 PDF 报告。
6. 失败时恢复旧镜像；若涉及数据迁移，则恢复升级前备份，禁止只回滚代码。

## 必须设置的监控

- `/healthz?detail=true` 连续失败或数据库状态异常。
- `FAILED` 作业数量增长、队列长时间无进展。
- 数据盘使用率、备份年龄和最近一次备份验证状态。
- 反向代理 5xx、请求超时和登录失败峰值。
- 容器退出、自动重启和宿主机不可用。

当前应用已有健康详情和站内作业提醒，但没有企业级集中告警出口。正式上线时应由企业现有监控平台轮询健康接口并触发短信、邮件或值班系统。

## 升级到高可用架构的触发条件

出现以下任一条件时，停止扩展单机 SQLite：

- 企业要求两个以上应用副本或跨主机自动故障转移。
- 数据库写锁、备份时间或恢复时间超过约定窗口。
- 上传数据超出单台虚拟机的安全容量。
- 扫描队列需要独立扩缩容，或应用重启明显影响任务处理。
- 企业要求跨机房容灾、对象级保留策略或数据库时间点恢复。

下一阶段架构应改为 PostgreSQL + S3 兼容对象存储（可用企业 MinIO）+ 独立任务队列/Worker。当前代码尚未实现这些适配，不能通过简单修改 Compose 副本数冒充高可用。

## 本地上线准入

只有以下证据全部形成后，才标记为“企业内网生产部署”：

- 未登录访问和伪造身份头均被拒绝。
- 两个企业空间之间的任务、报告和原文件不能互访。
- 重启后待处理作业能恢复，取消任务不会重新启动。
- 最近备份验证通过，隔离恢复的数据库完整性、任务数和文件数一致。
- TLS、端口、服务账号、数据目录权限和密钥注入通过企业安全检查。
- OCR 是否出网及其数据处理边界得到企业书面确认。
- 监控平台能在服务停止、数据库异常、备份过期和作业失败时告警。

## 当前结论

本方案可以把 BidProof 从“个人电脑 + Cloudflare Tunnel 公网试点”迁移为“企业控制的内网单节点部署”。它能显著改善数据归属、稳定运行和运维责任边界，但仍不是高可用集群。正式高可用需要数据库、对象存储和任务队列的下一轮工程改造。
