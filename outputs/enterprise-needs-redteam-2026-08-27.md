# BidProof 企业需求红队复核

日期：2026-08-27

## 被复核的结论

“工程产品已经基本成熟，剩下的主要只是拿到真实企业任务做业务验收；其他能力缺口不再影响企业使用。”

## 前提层

这个结论把“能试运行”当成了“企业可用”。当前证据只证明本地 FastAPI + SQLite、Cloudflare Tunnel 试点入口、规则定位、人工复核、批量管理、备份演练和 96 条自动化测试通过；没有证明多租户在真实组织中的长期运行、文件生命周期、身份合规或故障恢复时限。公网仍依赖本机进程和本地磁盘，不能推出生产连续性。

## 推理层

“准确度只差真实任务”省略了两个必要中间环节：第一，真实任务必须包含完整人工标签、漏项/误报复核、耗时和最终结果，否则仍然无法计算可解释指标；第二，即使真实任务表现合格，也不能推出身份、存储、通知、监控和合规能力已经满足企业采购。当前指标接口会在覆盖不足、样本少于 20 或复核未完成时保持 `INSUFFICIENT`，这是正确的边界，不是准确率证明。

## 执行层

企业用户会依赖尚未完成或未被真实验证的节点：

| 用户需要 | 当前状态 | 影响 |
| --- | --- | --- |
| 上传长任务可观察、失败可恢复 | 有进度、失败原因、重试；取消、断点续传和大文件压力未验收 | 首个真实大文件可能造成等待或重复上传 |
| 批量归档/删除/导出 | 已有接口和 UI；删除为永久删除，撤销窗口和导出范围确认未形成业务证据 | 误操作风险仍由用户承担 |
| 要求解释与证据定位 | 已有定位、引用、风险影响、建议动作和人工反馈 | 规则仍是未校准启发式，不代表法律或投标结论 |
| 协作整改 | 已有负责人、截止日期、状态、评论、审计和站内提醒 | 尚无邮件、企业微信、飞书等外部通知 |
| 企业账号治理 | 有 OWNER/ADMIN/REVIEWER/VIEWER 和会话 Cookie | 无密码找回、MFA/SSO、会话撤销和离职自动回收 |
| 数据持续性 | 已有 SQLite 备份、清单和隔离恢复演练 | 线上仍是本地 SQLite/文件；无对象存储、加密轮换、RPO/RTO 承诺 |
| 运营与采购验收 | 有 `/healthz`、审计导出、用量统计 | 无集中指标、告警、限流/配额、错误追踪、计费与发票 |
| 合规与安全 | 有扩展名/签名/宏/活动内容/压缩包安全检查 | 无病毒引擎、敏感信息脱敏、水印和可证明删除报告 |

## 反馈层

如果判断错误，最危险的不是马上报错，而是企业在关键投标截止日前才发现：某类表格/扫描件漏项、任务失败没有外部告警、或本机磁盘/进程不可用。当前没有真实企业任务、没有真实耗时基线，也没有 RPO/RTO、告警触达和恢复时限的现场数据，所以错误可能静默积累到业务结果之后才暴露。

## 精准度结论

当前判断应拆成三句话：

1. **工程层：高置信度可试运行。** 96 条测试、工作流检查、认证隔离、报告定位、作业重试和备份恢复均有本地证据。
2. **业务层：低置信度，尚未开始。** 真实任务 0、人工确认任务 0、付款信号 0；不能宣称真实召回率、漏报率、节省时间或成熟度。
3. **生产层：明确未完成。** 对象存储、SSO/MFA、外部通知、集中监控、配额/计费、病毒与敏感信息治理仍是企业部署缺口。

## 证伪事件

如果在首个真实企业任务完成后的 14 天内，仍无法为每个任务留存“原始文件哈希、人工确认标签、漏报/误报记录、处理耗时和最终投标结果”这五类可审计证据，那么“只差真实企业任务”这个判断就是错的。
